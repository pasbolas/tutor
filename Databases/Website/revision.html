Databases 1: Functions & Subqueries

?Functions vs subqueries: what's the actual difference?

Both are tools for pulling more useful information out of a query, but they work in completely different ways. A function takes some input and transforms it into a single output value, right there in your SELECT list, WHERE clause, or wherever you use it. A subquery is a whole separate SELECT statement living inside a bigger query, and its job is to first go fetch a value (or a set of values) that the outer query then uses.

Put simply: a function reshapes or calculates something from the data you already have in front of you. A subquery goes and gets you data you don't have yet, often from somewhere else in the table (or another table entirely), and hands it back so the main query can use it.

Functions

  • Operate on a value that is already part of the row or query (a column, an expression, or a constant).
  • Single-row functions return one result per row, e.g. UPPER(name).
  • Aggregate functions return one result per group of rows, e.g. AVG(wage).
  • Can be nested inside each other, e.g. ROUND(AVG(wage)).
  • Examples: nullif, coalesce, round, trunc, mod, to_char, upper, concat, count, sum.

Subqueries

  • A full SELECT statement nested inside another SELECT, INSERT, UPDATE, or DELETE.
  • The inner query runs first, and its result feeds into the outer query.
  • Single-row subqueries return exactly one value, so you compare with =, >, < etc.
  • Multiple-row subqueries return a list of values, so you use IN, ANY, ALL, EXISTS.
  • Can sit in a WHERE clause, a FROM clause (as a derived table), or even inside an UPDATE's SET clause.

They're not mutually exclusive either. You'll see them combined all the time, like a function wrapped around the result of a subquery, e.g. ROUND(MAX("Average wage"), 2) where the "Average wage" is coming from a subquery in the FROM clause.

Spotting the difference inside one query

Same query as above, but with every function underlined in one colour and the subquery underlined in another, so you can see exactly which part is doing which job.

SELECT ROUND(MAX("Average wage"), 2) "Maximum wage"
FROM (
    SELECT AVG(wage) "Average wage"
    FROM player_contracts
    GROUP BY club_id
) "Subquery";
Function — reshapes or calculates a value from data already in front of it (ROUND, MAX, AVG) Subquery — a separate SELECT nested inside, run first to fetch data the outer query then uses
ASQL Functions
Functions are pre-built pieces of functionality you can run on your data without writing the logic yourself. There are two broad families: single-row functions, which return one result per row, and multiple-row (aggregate) functions, which collapse a whole set of rows down into one result.
Single-row functions
Single-row vs multiple-row functions

Single-row functions look at each row individually and hand back a value for that row. A few things worth remembering about them:

  • They act on each row separately and return exactly one value per row.
  • They can be nested inside one another.
  • The value they return isn't always the same data type as the value that went in.
  • The argument they take can be a column, an expression, or a constant you type in yourself: function_name(arg1, arg2, ...).
  • You can use them in SELECT, WHERE, ORDER BY, and even in constraints.

Single-row functions fall into five categories:

  • Conversion: converts a value from one data type to another.
  • Character: takes character input and can return either a character or a numeric value.
  • Number: takes numeric input and returns a single numeric value.
  • Date: works on the date data type and returns a date.
  • General: handles NULL values, or picks a return value based on a condition.

Multiple-row (aggregate) functions do the opposite: instead of one value per row, they return one value for a whole set of rows, like COUNT, AVG, or SUM.

There's more than one way to concatenate, and they don't all behave the same with NULLs:

  • || joins values together, but if any one of them is NULL the whole result becomes NULL: 'a' || NULL → NULL.
  • concat() quietly skips NULLs instead of poisoning the whole result: concat('a', NULL) → 'a'. Since we usually want to keep whatever isn't null, concat() is generally the safer choice.
  • concat_ws(sep, args...) stands for "with separator". It takes a separator plus a list of arguments, joins them with that separator, and skips any NULLs along the way.
SELECT 'a' || NULL;
SELECT concat('a', NULL);
SELECT concat_ws(' , ', 'a', NULL, 'b');

Single-row functions can also be nested inside each other, and PostgreSQL evaluates them from the innermost one outward: F3(F2(F1(col,arg1),arg2),arg3) runs F1 first, then F2 on that result, then F3 on that.

SELECT lastname,
       UPPER(CONCAT(SUBSTRING(REGEXP_REPLACE(lastname, '\s+', '', 'g') FROM 1 FOR 8), '_IRL')) "Tag"
FROM scientist JOIN university USING (uni_id)
WHERE university.country = 'Ireland' LIMIT 15;

Custom functions: PL/pgSQL

PL/pgSQL (Procedural Language/PostgreSQL) lets you write your own reusable blocks of logic when a plain query isn't enough. It extends ordinary SQL with programming basics like loops and conditionals, and it's commonly used to build triggers, which are functions that fire automatically whenever a row is inserted, updated, or deleted.

The basic syntax looks like this:

CREATE OR REPLACE FUNCTION function_name(parameter_name data_type)
RETURNS return_type AS $$
BEGIN
    RETURN something;
END;
$$ LANGUAGE plpgsql;

Here's a function that works out whether a project is active, upcoming, or completed based on today's date:

CREATE OR REPLACE FUNCTION get_project_status(begin_d DATE, end_d DATE)
RETURNS TEXT AS $$
BEGIN
    IF current_date BETWEEN begin_d AND end_d THEN
        RETURN 'Active';
    ELSEIF current_date < begin_d THEN
        RETURN 'Upcoming';
    ELSE
        RETURN 'Completed';
    END IF;
END;
$$ LANGUAGE plpgsql;

SELECT research_id,
       title,
       get_project_status(begin_date, end_date) AS project_status
FROM research LIMIT 5;

A row-level trigger example, which recalculates a derived value every time a new row comes in:

CREATE OR REPLACE FUNCTION set_plus_minus_row()
RETURNS TRIGGER AS $$
BEGIN
    NEW.plus_minus_points := NEW.points - NEW.turnovers;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_plus_minus_row
BEFORE INSERT ON player_statistics
FOR EACH ROW
EXECUTE FUNCTION set_plus_minus_row();

And a statement-level trigger, which recalculates the value across every row at once. Note it returns NULL, because statement-level triggers are required to:

CREATE OR REPLACE FUNCTION update_plus_minus_all()
RETURNS TRIGGER AS $$
BEGIN
    UPDATE player_statistics SET plus_minus_points = points - turnovers;
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_plus_minus_statement
AFTER INSERT ON player_statistics
FOR EACH STATEMENT
EXECUTE FUNCTION update_plus_minus_all();
Aggregate (group) functions
Aggregate (group) functions

Aggregate functions take a whole bunch of rows and collapse them down into a single value. Because of that, if a query mixes an aggregated column with a normal, non-aggregated column, PostgreSQL needs a GROUP BY clause to know how to group the rows together first.

COUNT(*)
Counts how many rows are in a table. Because it's counting rows rather than a specific column's values, NULLs still get counted. If you count a specific column instead, e.g. COUNT(wage), rows where that column is NULL are skipped.
SELECT COUNT(*) "Total players"
FROM players;

-- ignores NULL wage
SELECT COUNT(wage) "Contracts with wage"
FROM player_contracts;

SELECT COUNT(DISTINCT club_id) "Unique wage values"
FROM player_contracts;

You can also use subqueries to gather several different counts side by side in a single row of output:

SELECT (SELECT COUNT(player_id) FROM players) "Total number of players",
       (SELECT COUNT(club_id) FROM clubs) "Number of clubs",
       (SELECT COUNT(DISTINCT player_id) FROM player_attributes) "Number of players with attributes",
       (SELECT COUNT(DISTINCT player_id) FROM player_contracts) "Number of players with contracts";
GROUP BY
Groups rows together based on the value of one or more attributes, so an aggregate function can be applied to each group separately. You can group by more than one column at once to get summaries at different levels of detail.
SELECT club_name,
       COUNT(player_contracts.player_id) "Players with contract"
FROM clubs LEFT JOIN player_contracts USING (club_id)
GROUP BY club_name;

SELECT club_name,
       nationality,
       ROUND(AVG(wage), 2) "Average wage"
FROM player_contracts JOIN players USING (player_id) JOIN clubs USING (club_id)
GROUP BY club_name, nationality
ORDER BY 2, 3 DESC;

A common point of confusion is WHERE versus HAVING. PostgreSQL actually runs a query in this order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. WHERE filters individual rows before they're grouped, which means it can never contain an aggregate function, because the aggregate simply doesn't exist yet at that stage. HAVING is the one that filters after the grouping and aggregation have already happened.

-- This fails: WHERE cannot use an aggregate
SELECT club_id,
       ROUND(AVG(wage), 2) "Average wage"
FROM player_contracts
GROUP BY club_id
WHERE AVG(wage) > 50000;
Example: fixing it with HAVING
SELECT club_id,
       ROUND(AVG(wage), 2) "Average wage"
FROM player_contracts
GROUP BY club_id
HAVING AVG(wage) > 50000;

FILTER (WHERE ...)
Applies a condition to one specific aggregate, without touching the rest of the query. Reach for FILTER when you want several aggregates with different conditions side by side in the same row, and reach for HAVING when you want to drop entire groups based on the aggregate result.
SELECT club_name FILTER (WHERE club_name IS NOT NULL),
       COUNT(player_id),
       COUNT(player_id) FILTER (WHERE wage IS NOT NULL) "With wage",
       COUNT(player_id) FILTER (WHERE wage IS NULL) "Without wage"
FROM clubs LEFT JOIN player_contracts USING (club_id)
GROUP BY club_name ORDER BY club_name;

One rule that catches people out: SQL will not let you nest one aggregate directly inside another, so something like MAX(AVG(wage)) throws an error, because aggregation only happens once per query block, right after GROUP BY runs. The workaround is to compute the first aggregate in a subquery, then aggregate over that result. Notice that ROUND and MAX can still nest together here, because ROUND is a single-row function, not an aggregate:

SELECT ROUND(MAX("Average wage"), 2) "Maximum wage"
FROM (

BSubqueries
A subquery is simply a query nested inside a bigger query. It can live inside a SELECT, INSERT, UPDATE, or DELETE statement, or even inside another subquery. The inner query (the subquery) runs first, and whatever it returns is then used by the outer query.
Basics & comparison subqueries
Subquery in a WHERE clause: the basic pattern

The general shape is: run the inner query first, then let the outer query use whatever it produced.

SELECT attribute_name FROM table_name
WHERE condition (SELECT attribute FROM table_name WHERE condition);
Single-row subqueries

A single-row subquery returns just one row, so you can compare against it using ordinary single-row operators like =, >, <. For example, finding players who earn more than the average wage:

SELECT p.player_name,
       pc.wage
FROM players p JOIN player_contracts pc USING (player_id)
WHERE pc.wage > (SELECT AVG(wage) FROM player_contracts);

You can also chain several single-row subqueries together with AND to build more complex conditions. Here we want players who earn more than Chelsea's top earner and are worth more than the average Real Madrid player:

SELECT p.player_name,
       pc.wage
FROM players p JOIN player_contracts pc USING (player_id)
WHERE pc.wage > (
    SELECT MAX(wage) FROM player_contracts WHERE club_id = 'CL137'  -- Chelsea
) AND pc.value > (
    SELECT AVG(value) FROM player_contracts WHERE club_id = 'CL473'  -- Real Madrid
);

EXISTS
EXISTS
Checks whether the subquery returns any rows at all, and simply returns true if it finds at least one. SELECT 1 is the usual shorthand you'll see inside an EXISTS subquery, since the actual value being selected doesn't matter, only whether a matching row exists.
-- Clubs that currently have at least one player earning over 50k/week
SELECT c.club_id,
       c.club_name
FROM clubs c
WHERE EXISTS (
    SELECT 1 FROM player_contracts pc
    WHERE pc.club_id = c.club_id AND pc.wage >= 50000
);

Multiple-row subqueries: IN, NOT IN, ANY, ALL

These subqueries can return more than one row, so they pair with comparison operators built to handle a whole list of values rather than just one:

  • IN checks whether a value matches any single value in the list the subquery returns.
  • NOT IN is the opposite, checking that a value matches none of them.
  • ANY compares a value against every value the subquery returns, and passes if the condition is true for at least one of them.
  • ALL also compares against every value returned, but only passes if the condition is true for every single one.

IN: finding players contracted to clubs that have at least one high earner (€50,000 or more):

SELECT p.player_name,
       c.club_name,
       pc.wage
FROM players p JOIN player_contracts pc USING (player_id) JOIN clubs c USING (club_id)
WHERE pc.club_id IN (
    SELECT DISTINCT club_id FROM player_contracts WHERE wage >= 50000
);

Advanced subquery techniques
Subquery in FROM (a derived table)

A subquery doesn't have to live in WHERE. You can put one in the FROM clause too, and PostgreSQL will treat it just like a regular table. This is exactly the trick used to get around SQL's rule against nesting aggregates directly:

SELECT ROUND(MAX("Average wage"), 2) "Maximum wage"
FROM (
    SELECT AVG(wage) "Average wage" FROM player_contracts GROUP BY club_id
) "Subquery";

PostgreSQL first runs the inner query and materialises it as if it were a real table called "Subquery", with one "Average wage" row per club. The outer query then just does MAX/ROUND over that small table.

Subquery vs JOIN

The same result can often be written either as a correlated subquery or as a JOIN, and they're not always equal in performance. A JOIN generally runs faster because the column being matched on, like an ID, can be used almost like an index for quick lookups. A scalar subquery, on the other hand, effectively runs once for every row in the outer query, which adds up.

-- Using a SUBQUERY
EXPLAIN ANALYZE SELECT game_id,
       (SELECT team_city FROM nba.teams t WHERE t.team_id = g.home_team_id) AS home_city
FROM nba.games g;

-- Using a JOIN
EXPLAIN ANALYZE SELECT game_id,
       team_city "Home city"
FROM games g JOIN teams t ON (t.team_id = g.home_team_id);

The difference shows up in EXPLAIN ANALYZE's timing output: the subquery version re-runs a lookup against nba.teams for every single game row, while the JOIN version matches team_id once using an efficient join strategy, so it typically comes back faster on a large games table.

UPDATE with a subquery

Subqueries aren't just for reading data, they can feed straight into an UPDATE. Here every player with a NULL wage gets set to the average wage of everyone else:

UPDATE player_contracts
SET wage = (
    SELECT ROUND(AVG(wage)) FROM player_contracts WHERE wage IS NOT NULL
)
WHERE wage IS NULL;

CTE as an alternative to a subquery
WITH name AS (...)
A Common Table Expression computes a result once, gives it a name, and lets you query it like a temporary table afterwards. It reads much more clearly than nesting everything inside one giant SELECT, even though it's solving the same kind of problem a subquery would.
WITH player_avg AS (
    SELECT person_id, AVG(points) AS avg_points
    FROM player_statistics
    GROUP BY person_id
)
SELECT person_id,
       avg_points
FROM player_avg
WHERE avg_points >= 20
ORDER BY avg_points DESC;

CASE combined with functions and subqueries

CASE can wrap around an aggregate function to sort groups into categories based on where their aggregate value lands:

SELECT c.club_name,
       ROUND(AVG(pc.wage)) "Average wage",
       CASE
    WHEN AVG(pc.wage) >= 40000 THEN 'High Budget Club'
    WHEN AVG(pc.wage) BETWEEN 10000 AND 39999 THEN 'Medium Budget Club'
    WHEN AVG(pc.wage) < 10000 THEN 'Low Budget Club'
    ELSE 'No Data'
END "Budget category"
FROM clubs c JOIN player_contracts pc USING (club_id)
WHERE pc.wage IS NOT NULL
GROUP BY c.club_name
ORDER BY AVG(pc.wage) DESC;
